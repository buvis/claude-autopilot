## 1 of 30 - MEDIUM - From inside its own process tree, the live loop is invisible, and a registry prune deletes its entry

**What.** The loop registry check (`loop_gates._child_pids`, also `tracon/discovery._child_pids` and `procinfo.child_names`) lists a wrapper's children with `pgrep -P`. On macOS, `pgrep` silently leaves out the caller's own ancestors unless `-a` is given. Every process the loop spawns (its sessions, this agoge run, a nested `autopilot loop`) therefore sees the registered wrapper as childless, so the duplicate-loop guard and `wave launch`'s "a loop is already running" refusal are blind, and `prune_registry` deletes the live entry. Found by heidi (integration) and trudy (security).

**Evidence (confirmed).** Real tree via `proc_pidinfo`: `bash 62875 (registry pid) -> python3.14 62886 (exec_env _AUTOPILOT_LOOP=62875) -> caffeinate 62887`. `pgrep -l -P 62875` -> exit 1, nothing; `pgrep -a -l -P 62875` -> `62886 python3.14`. `live_wrapper_pid(<repo>, ~/.claude/autopilot-loops)` -> `None` with both HEAD and the 0.9.0 cache while the loop was alive. On a **copy** of the registry, `prune_registry` left `[]`: the live entry was deleted. The real registry was not touched. This also explains recon's puzzle: `pgrep -P 62887` is empty because caffeinate is a leaf.

**If unchanged.** Any session the loop starts can launch a second loop or a wave on the same checkout, and its registration prunes the incumbent's entry. That is the "foreign edits" and "two loops" failure class this repo already pays for. Likely whenever a session runs a registry-touching verb. Hits 0.9.0 today. Stable.

**Options.**
1. **(Recommended) Add `-a` to the three `pgrep -P` calls.** Benefit: one-flag fix, matches the product's own test helper (`codex_run_test_lib.sh:77`). Drawback: still shells out to `pgrep`, which the sandbox could restrict later. Effort S. Could break: Linux `pgrep` has no `-a` with this meaning (it prints full command lines), so gate it to Darwin or use `procinfo` there. Strongest reason against: a per-platform flag is easy to regress.
2. Read the parent pid from libproc (`proc_pidinfo` PROC_PIDTBSDINFO ppid, or `proc_listchildpids`) in `procinfo`, and use that everywhere. Benefit: no `pgrep` at all, same path as `exec_env`. Drawback: more ctypes code with no Linux twin. Effort M. Could break: the untested Linux branch.
3. Register the tagged driver pid (62886) instead of the bash wrapper. Benefit: the tag check no longer needs children. Drawback: changes the registry contract other tools read (tracon). Effort M.
4. Accept or defer.

Test: from a grandchild process, `live_wrapper_pid` finds a registered grandparent whose child carries the tag (`cli/test_loop_gates.py`).
