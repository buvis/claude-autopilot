## 1 of 32 - HIGH - `carry` makes any review row, a 🔴 included, vanish with no task and no record

**What:** PRD 00264 added a `carry` disposition for rows already re-queued as `[C{cycle}]` tasks. Nothing checks that such a task exists, or that the ref is even in the review (`skills/run-autopilot/cli/gate.py:141` puts `carry` in `_SKIPPED_CLASSIFICATIONS`, and `review_close.py` never looks it up). Found by heidi, wendy and trudy separately. Recon flagged it first.
**Evidence (confirmed):** heidi's run started from a review with R1 🔴 "deletes user data", R2 🟠 and R3 🟡, with findings R1 `carry`, R2 `carry`, R3 `discard`. `gate` exited 0. `review-close --batch-id decision-gate` printed `"tasks_created": []`, and `'deletes user data' in state.json` -> False. Then `phase-done --outcome converged` returned `next_phase: done`. The review coverage hook exited 0, and `render audit` printed `no decisions recorded`. A ghost `carry` for R99 🔴 (not in the review) also exits 0. The 0.9.0 cache refuses that ghost with exit 2, so 00264 opened this hole.
**If unchanged:** once 00264 ships, a model that writes `carry` (by mistake or to save work) can converge a PRD with an open critical finding and leave no trace in state or the audit. It is likely, because `carry` is the documented shape for the most common 🔴 case. It stays hidden and does not get louder over time.
**Options:**
1. **(Recommended) Back `carry` against state.** Refuse a `carry` row unless its ref is in the review table and a `[C{cycle}]` task exists for it (`refused: "carry_unmatched"`, exit 2, checked before the lock). Benefit: closes the hole at the one place every batch passes. Drawback: needs a ref-to-task link that `[C]` tasks may not carry today, so it may fall back to file+severity matching. Effort M (guess). Could break: a real re-queue whose task title does not match would now be refused.
2. **Drop `carry` from `_SKIPPED_CLASSIFICATIONS`** so it is at least backed against the review table, and refuse `carry` on 🔴 rows unless a matching `[C]` task exists. Benefit: smaller; kills ghost refs. Drawback: a 🟠/🟡 `carry` still creates nothing unchecked. Effort S. Could break: little.
3. **Record every `carry` as a decision** (`autonomous_decisions` entry naming the task it claims), so the audit shows it even when nothing is checked. Benefit: visibility with no refusals. Drawback: shows the problem without preventing it. Effort S.
4. Accept or defer.
**Strongest reason against #1:** it puts a ref-to-task matching rule into `review_close`, and a fuzzy match can refuse a legitimate batch mid-loop.
**Fix test:** `test_carry_on_critical_without_requeued_task_is_refused` in `cli/test_review_close.py`, built from heidi's payload.

## 2 of 32 - HIGH - A 🔴 row escapes the coverage check when the table is off-shape, has no Ref column, or uses bullets

**What:** the 00264 coverage check only sees rows that match `TABLE_DATA_ROW_RE` and carry a Ref (`skills/run-autopilot/cli/gate.py`, around line 256 and the row regex). It skips every other row without a word. Found by walter (no Ref column or bullets) and trudy (off-shape cells, duplicate refs).
**Evidence (confirmed):** with R1 🔴 left out of the findings JSON, changing only R1's cell to `| r1 |`, `| R1. |`, `| R1a |` or `| R1 \| R3 |`, or writing consensus `2/2` without brackets, gave `gate` 0, `review-close` 0 and `tasks_created: []`. The control `| R1 |` gives exit 2. walter's review files with no Ref column, or with bullet rows, closed with `[]` findings and zero tasks. A 🔴 row labelled with a duplicate `R2` also passed. A ref listed twice with two different classifications was accepted.
**If unchanged:** the coverage check promises "every row gets a disposition", but small format drift in reviewer output (case, punctuation, a table without Ref) silently turns it off. Reviewer output is model-written, so drift is likely. Each case stays hidden, and the batch key is spent, so a corrected re-run gets `already applied`.
**Options:**
1. **(Recommended) Fail closed on rows that do not parse.** Once a header is found, every later pipe row that is not a separator is a data row; one that does not parse makes the table `unreadable` (exit 2). Drawback: more refusals in the loop, and each one costs a round trip. Effort M. Could break: older review files with odd rows that used to pass.
2. **Cover Ref-less rows by (severity, file, issue)**, the key `_backed` already uses. Benefit: bullet and Ref-less reviews stay usable. Drawback: fuzzy keys, and still silent on off-shape refs. Effort M.
3. **Require a Ref column in the reviewer templates and prose**, and leave the parser alone. Benefit: no code risk. Drawback: depends on the model following prose. Effort S.
4. Accept or defer.
**Strongest reason against #1:** a stricter parser turns harmless formatting noise into stuck loops until the reviewer prompts are tightened too.
**Fix test:** `rejects_review_row_with_offshape_ref_instead_of_skipping_it`, parametrized over the five cells, plus a Ref-less 🔴 table with `[]` findings, in `cli/test_gate_findings_table.py` and `cli/test_review_close.py`.
