## V49. The Edit/Write tool decodes `\uXXXX` in its arguments

Writing `"‑"` into an Edit or Write argument makes the TOOL decode it: the
file receives the actual non-breaking hyphen, not the six-character escape.

Observed twice on task 1. Round two of Tess's test file came back carrying 32
pasted invisible/combining code points even though her report said "every
lookalike stays an escaped literal" - she had written escapes and the tool
decoded them. A later Tess dispatch diagnosed it herself and worked around it
by generating the literal backslashes from a throwaway script outside the repo.

I first blamed the known loupe reflow, and that was WRONG. Loupe's reflow was
also present in the same session (exploded signatures and trailing commas in
`hooks/guard_phase_delegation.py`, twice, which I reverted both times) but it
never touched the escapes. Two different corruptions, two different causes.

Why it matters here: a test file whose entire subject is lookalike code points
is unreadable and self-destroying once the characters are pasted. The file's
own docstring says exactly that.

How to handle it:
- After any subagent writes escaped code points, AUDIT the file rather than
  trusting the report. A per-line `unicodedata.category` dump proves it;
  `rg -c --pcre2 "[^\x00-\x7F]"` with a known-hit control file is the cheap
  version.
- To repair, convert with a script (read the file, re-emit every non-ASCII
  character as `\uXXXX`) and prove equivalence by comparing the AST's string
  constants before and after. On this file that compared 143 constants, found
  nothing changed, and made the rewrite safe to commit.
- Tell a subagent editing such a file that the tool decodes escapes, so it
  reaches for a script instead of an Edit argument.

**Promote to memory**: this belongs in the project auto-memory next to
`project-loupe-reflows-edited-py-files-at-turn-end`, which currently gets the
blame for it. The write-scope fence blocks a batch from writing `~/.claude`, so
it could not be saved from the session that found it.

## V50. The contract gap a passing suite hid

Task 1's contract (verbatim in the task description, from the design doc) says
`_normalize` maps "every `Pd` code point and U+2212" to `-`. The implementor
instead folded the literal range U+2010..U+2015, and all 45 tests passed,
because Tess had only sampled dashes from inside that range.

A one-off sweep over all of Unicode against the shipped module found 15 `Pd`
code points unfolded, and `/autopilot:plan<U+301C>tasks` (wave dash) was
ALLOWED where the contract requires a denial. That is a live guard bypass that
the green suite did not see.

Cost to close: one Tess dispatch for two out-of-range pins, one Ivan repair.
Afterwards the sweep reported 0 unfolded and the wave-dash dispatch denied.

Lesson: for a contract phrased as a Unicode CATEGORY (or any other family
rule), a sampled test table cannot distinguish the family from a range that
happens to contain the samples. Either pin at least one member outside the
obvious range, or sweep the family once in the orchestrator and treat the sweep
as evidence. Devon did not catch this: he attacks the tests, and a
narrower-than-contract implementation passes the tests by construction.

which it was.

measured re-checks on 2026-09-25/26 changed nothing): on a task whose subject is
an adversarial input filter, he found the real holes. Worth keeping the tier
gate rather than widening or dropping it.
